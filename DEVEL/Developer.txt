4. configuration de git

NOTE : ces instructions supposent que vous êtes sur la branche par défaut ;
      c'est _bien_ là que vous devez être pour la mise en place.  Ce n'est
      pas forcément la branche que vous utiliserez pour vos modifications ;
      consultez la documentation privée du projet concerné pour plus
      d'informations (si vous travaillez seul, nous vous suggérons des noms
      de branche commençant par « LOCAL- »).

NOTE : les instructions suivantes nécessitent perl.  Si perl n'est pas
      présent sur votre système, installez-le avant de continuer.

NOTE : avant l'installation, des informations complémentaires sur
      nhgitset.pl sont disponibles via :
           perldoc DEVEL/nhgitset.pl
      Après l'installation, les mêmes informations sont disponibles avec :
           git nhhelp nhgitset

A. Si vous n'avez jamais configuré git sur cette machine :
   (Ceci suppose que vous n'utiliserez git que pour NetHack.  Si vous comptez
   l'utiliser aussi pour d'autres projets, réfléchissez avant de taper.)
	Indiquez à git le nom (ou pseudonyme) et l'adresse e-mail à utiliser :
		git config --global user.name "MY NAME"
		git config --global user.email USER@EXAMPLE.COM
   Vous voudrez probablement mettre en place un cache d'identifiants.
	macOS (10 ou ultérieur) :
	    git config --global credential.helper osxkeychain
	Linux :
	    (Cela dépend de la distribution.)
	    cd /usr/share/doc/git/contrib/credential/libsecret
	    sudo apt-get install libglib-2.0-dev libsecret-1-dev
	    sudo make
	    git config --global credential.helper `pwd`/git-credential-libsecret
		OU
	    sudo yum install git-credential-libsecret
	    git config --global credential.helper /usr/libexec/git-core/git-credential-libsecret
	Windows : (les trois cas suivants supposent que Git for Windows est
	          déjà installé sur le système Windows sous-jacent,
	          https://git-scm.com/download/win) :
	    git config --global credential.helper store
          Shell bash MSYS2 UCRT64 :
            git config --global credential.helper "/c/Program\ Files/Git/mingw64/bin/git-credential-manager.exe"
	  Shell bash Windows Subsystem for Linux 2 (WSL2) :
            git config --global credential.helper "/mnt/c/Program\ Files/Git/mingw64/bin/git-credential-manager.exe"
B. Indiquez le préfixe pour la substitution de variables :
   (Ceci suppose que vous n'êtes membre ni de la DevTeam ni de l'équipe de
   développement d'une variante.  Si vous l'êtes, ceci peut être erroné.
   Recherchez une documentation plus spécifique.  Par exemple, ce fichier
   utilise « MINE » comme préfixe de substitution - ce sera presque toujours
   faux si vous travaillez avec quelqu'un d'autre.)
	Choisissez où placer ces informations ; elles ne doivent PAS se
	trouver dans l'arborescence clonée depuis git.  J'utilise
	~/nethack/GITADDDIR ; pour cette base, créez les répertoires
	nécessaires et éditez le fichier :
		~/nethack/GITADDDIR/DOTGIT/PRE
	Mettez-y ceci, en l'adaptant à votre variante (si votre système n'est
	pas de type Unix, vous devrez peut-être modifier la première ligne) :
		#!/bin/sh
		git config nethack.substprefix MINE
		git config nethack.projectname MineHack
	Rendez-le ensuite exécutable :
		chmod +x ~/nethack/GITADDDIR/DOTGIT/PRE
C. Configurez le dépôt :
	- placez-vous (cd) à la racine du dépôt
	- indiquez au dépôt le répertoire créé ci-dessus :
		git config nethack.gitadddir FULL_PATH_TO_GITADDDIR
	   soit, pour l'exemple ci-dessus :
		git config nethack.gitadddir ~/nethack/GITADDDIR
	- lancez la configuration automatique :
		perl DEVEL/nhgitset.pl
	  S'il se plaint, corrigez ce dont il se plaint.  nhgitset.pl accepte
	  les options suivantes :
		-v mode verbeux
		-n simulation (rien n'est modifié)
   Vous pouvez relancer nhgitset.pl aussi souvent que nécessaire ; il nous
   arrive de le mettre à jour (ou de mettre à jour un élément qu'il installe)
   et vous devrez alors le relancer pour que les changements prennent effet.
D. Alias
   nhgitset.pl installe deux alias :
	nhadd
	nhcommit
   Ces deux commandes acceptent les mêmes options que les commandes git add
   et commit habituelles, mais effectuent une substitution de variables à la
   manière de RCS/CVS.

   Notez qu'il ne se passera rien de grave si vous n'utilisez pas les
   versions nh* de ces commandes.

   Substitutions prises en charge :
	MINE-Date	la date et l'heure du commit
   Substitutions expérimentales :
	MINE-Revision	numéro de révision à la manière de CVS
	MINE-Branch	la branche git courante

   Pour accéder directement au mécanisme de substitution, utilisez :
	nhsub

   Voir la section « nhadd/nhcommit » pour les détails sur ces alias.
   Lancez « perldoc DEVEL/hooksdir/nhsub » pour les détails sur nhsub.

C'est tout.  Si vous avez besoin de faire autre chose lors de la mise en
place de votre dépôt, poursuivez la lecture.  Sinon, vous en avez terminé
avec cette section.

1) pour exécuter vos propres hooks en plus des nôtres :
	nommez votre hook
		WHEN-HOOKNAME
	où WHEN vaut
		PRE	(exécute votre code avant le hook de NetHack)
		POST	(exécute votre code après le hook de NetHack)
	et HOOKNAME est le nom git habituel du hook.
   Assurez-vous que les hooks sont exécutables (chmod +x ...).
   Testez soigneusement, car la composition de deux morceaux de code peut ne
   pas faire ce que vous voulez.
2) pour installer d'autres éléments lors de la mise en place :
	Placez les fichiers supplémentaires dans l'arborescence GITADDDIR.
	Utilisez « DOTGIT » au lieu de « .git ».  Si un fichier nommé PRE,
	POST ou INSTEAD existe dans un sous-répertoire de GITADDDIR, il est
	exécuté avant la copie, après la copie ou à la place de la copie.
	Aucune copie n'est tentée dans le répertoire DOTGIT ; utilisez un
	script et les commandes git standard pour en modifier le contenu
	selon les besoins.
3) N.B. : dans tous les espaces de noms, tout ce qui correspond à m/^nh/i ou
   m/^nethack/i est réservé.

5. expansion de variables
A. Introduction
   Nous avons mis en place un mécanisme d'expansion de variables à la
   manière de RCS/CVS/SVN.  Les références de l'un ou l'autre des formats :
	$PREFIX-VARNAME$
	$PREFIX-VARNAME: VALUE $
   seront traitées (si le mécanisme est activé).

   PREFIX est la valeur de la variable de configuration git
   nethack.substprefix.
   VARNAME est l'un des noms suivants :
	Date
	Branch
	Revision
   tout autre nom provoquera un avertissement.

B. Activation de l'expansion de variables
   L'expansion de variables est contrôlée par le fichier .gitattributes.

   Pour activer l'expansion de variables :
        pattern NHSUBST
   Pour désactiver l'expansion de variables :
	pattern -NHSUBST

   Plus d'informations : « git help gitattributes »

C. Bizarreries
   Pour déclencher l'expansion de variables, vous _devez_ utiliser
   « git nhadd » ou « git nhcommit » au lieu de « git add » ou
   « git commit ».  Il ne se passera rien de grave si vous utilisez la
   mauvaise commande, mais les valeurs ne seront pas mises à jour.

   L'expansion de variables modifie les fichiers de l'arbre de travail ;
   votre éditeur ou votre IDE ne l'apprécieront pas forcément.

D. Utilisation de vos propres hooks
   Vous pouvez utiliser vos propres hooks : placez-les comme d'habitude dans
   .git/hooks MAIS nommez-les ainsi :
	WHEN-HOOKNAME
   où WHEN vaut :
	PRE	(exécute le code avant le hook de NetHack)
	POST	(exécute le code après le hook de NetHack)
   et HOOKNAME est le nom git habituel du hook.

   Testez soigneusement : les interactions entre hooks peuvent être
   pénibles.

7. nhadd/nhcommit
   nhadd revient essentiellement à « git nhsub $*; git add $* »
   nhcommit revient essentiellement à « git nhsub $*; git commit $* »

   Comme « git add » et « git commit » ont des arguments complexes, nhsub
   tente de faire ce qu'il faut - ou du moins quelque chose de raisonnable -
   pour la plupart des arguments.  Si nhadd/nhcommit ne font pas ce dont vous
   avez besoin, lancez « git nhsub » seul, puis faites add/commit.

   Alors, quand faut-il utiliser quoi ?
   Le but est que nhsub soit exécuté juste avant que git ne prenne un
   instantané de chaque fichier.  Par exemple :
   - utilisez « git nhcommit <filespec> » au lieu de
     « git commit <filespec> »
   - utilisez « git nhadd <filespec> » au lieu de « git add <filespec> »
   - utilisez indifféremment « git commit » ou « git nhcommit » (car
     l'instantané a déjà été pris)
   - si vous utilisez « git nhsub <filespec> », vous pouvez ensuite faire
     « git add <filespec> » ou « git commit <filespec> »

   Pour des situations plus complexes, « git nhsub » accepte les options -v
   et -n - voir « perldoc DEVEL/hooksdir/nhsub ».

8. hooks

   nhgitset.pl installe aussi des hooks dans .git/hooks.  Ces hooks
   fournissent un cadre qui permet au code de hook local de coexister avec
   le code de hook que nous fournissons - voir DEVEL/hooksdir/NHgithook.pm
   pour les détails.

   Nous utilisons actuellement les hooks suivants :
    post-checkout
    post-commit
    post-merge
   Ils servent à générer dat/gitinfo.txt, qui fournit les données finalement
   accessibles via la commande de jeu #version et l'option de ligne de
   commande --version.
