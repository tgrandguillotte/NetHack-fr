Style de codage de la DevTeam de NetHack
========================================

NetHack est écrit en C, avec un peu de C++ pour accéder aux bibliothèques
des plates-formes. Ce document de style de codage porte principalement sur
le style utilisé pour les fichiers source C. Nous n'avons pas défini de style
pour les fichiers C++, mais le C++ doit être mis en forme dans l'esprit du C.

Peu avant la version 3.6, le code des fichiers C a été reformaté à l'aide
d'une version de l'outil clang-format modifiée pour prendre en charge les
déclarations d'arguments à la K&R. En raison de certaines incompatibilités,
ce correctif n'est pas disponible publiquement et clang-format n'est pas
destiné à être utilisé régulièrement.  Depuis, les déclarations et
définitions de fonctions sont passées au style ANSI.

Les développeurs doivent faire de leur mieux pour respecter le style de
codage, afin de favoriser un code lisible et facile à modifier. La lisibilité
prime : dans certains cas, il peut donc être préférable de ne pas suivre
entièrement les règles de style.

Des recettes pour les éditeurs de texte courants figurent à la fin de ce
fichier.

Indentation et espacement
-------------------------

L'indentation de base est de 4 espaces. Toute l'indentation se fait avec des
caractères espace, et non des tabulations.

Les lignes doivent faire au plus 78 caractères. Si une ligne doit dépasser
cette limite, elle doit être coupée et la partie renvoyée à la ligne doit
être alignée sur les parenthèses ou crochets qui contiennent la coupure.
S'il n'y a pas de parenthèses ni de crochets, la ligne doit être indentée de
quatre espaces. La coupure doit normalement se faire après une virgule ou
avant un opérateur binaire, lorsque c'est possible :

    int index
        = SomeExcessivelyLongExpression;

    fcall(arg1,
          arg2, (cond13
                 && cond2));

Des lignes vides isolées doivent être utilisées chaque fois que cela améliore
la lisibilité.

Fonctions et instructions de contrôle
-------------------------------------

Dans une définition de fonction, le type de retour, le déclarateur et
l'accolade ouvrante doivent chacun figurer sur une ligne distincte. Les
arguments sont définis dans les parenthèses qui suivent, selon la norme
ANSI.  Il existe deux styles généraux.  L'un sans commentaires, où les
arguments se suivent les uns après les autres, avec en cas de dépassement un
renvoi à la ligne aligné sur le premier argument.

    void
    foo(int i, char c)
    {
        /* function body */
    }

    void
    long_function_name(int first_arg, struct long_name *second_arg,
                       int third_arg, int forth_arg)
    {
        /* function body */
    }

Sinon, les arguments peuvent être placés un par ligne s'ils sont commentés :

    void
    long_function_name(int first_arg,                /* main operation */
                       struct long_name *second_arg, /* control details */
                       int third_arg,                /* local conditions - if
                                                        they apply */
                       int forth_arg)                /* remote conditions */
    {
        /* function body */
    }

Si la fonction ne prend pas de paramètres :

    int
    long_function_name(void)
    {
        /* function body */
    }

L'accolade ouvrante d'une instruction de contrôle figure sur la même ligne
que l'instruction de contrôle :

    if (condition) {
        /* body */
    }

Les instructions else et les instructions while des blocs do-while figurent
sur la même ligne que l'accolade fermante de l'instruction if ou do. Dans les
autres cas, l'accolade fermante a toujours sa propre ligne.

    if (condition) {
        /* body */
    } else if (condition) {
        do {
            /* body */
        } while (condition);
    } else {
        /* body */
    }

Si un bloc de contrôle ne contient qu'une seule instruction, celle-ci peut
figurer seule sur sa ligne, indentée. S'il s'agit d'une instruction vide,
elle doit être exprimée par un bloc vide et non par un point-virgule, car de
nombreux compilateurs émettent un avertissement en cas d'instruction vide :

    if (condition)
        fcall();

    if (condition) {
    } else
        fcall();

Si plusieurs blocs de contrôle se suivent, il peut être plus lisible
d'utiliser des accolades même pour des instructions uniques, et il faut les
utiliser si elles améliorent la lisibilité. Voici un exemple de mauvaise
pratique :

    if (condition) {
        /* long body */
    } else if (condition)
        statement;
    else {
        /* very long body */
    }

Dans les instructions switch, les étiquettes case ne sont pas indentées et
les instructions sont indentées normalement. Le cas default doit venir en
dernier, sauf raison impérieuse, et les passages au cas suivant
(fallthrough) doivent être signalés explicitement par un commentaire, pour
éviter que Yeenoghu ne récupère à nouveau le toucher de mort :

    switch (condition) {
    case FOO:
    case BAR:
        fcall();
        /* fall-through */
    case BAZ:
        fcall();
        break;

    default:
        statement;
    }

Les variables ne doivent jamais être déclarées dans une condition ni dans
l'initialisation d'une boucle for, et si une affectation sert de condition,
elle doit être placée dans une paire de parenthèses supplémentaire par souci
de clarté :

    int *p;
    if ((p = fcall())) {
        /* body */
    }

    int i;
    for (i = 1; i < 10; ++i) {
        /* body */
    }

Noms de variables à éviter
--------------------------

    near, far    Certains compilateurs et compilateurs croisés ciblant
                 d'anciens processeurs à architecture segmentée peuvent les
                 traiter comme des mots-clés. Le plus sûr est de les éviter.

    NEARDATA     Certaines données sont marquées avec cette macro ; le
                 portage Amiga l'utilise pour marquer les données à utiliser
                 avec un mode d'adressage court. Vous n'avez pas besoin de
                 l'utiliser.

static ou staticfn
------------------

La macro staticfn vaut soit « static », soit rien (voir config.h).  Si
possible, les fonctions de src/*.c qui seraient autrement marquées static
doivent être marquées staticfn, afin que l'on puisse forcer les plates-formes
qui ne nomment pas les fonctions statiques dans leurs traces d'appels à le
faire ; cela implique que les noms de fonctions ne peuvent pas être
réutilisés.  N'utilisez jamais staticfn pour des données.

Espaces dans les expressions
----------------------------

Les espaces doivent figurer autour des opérateurs binaires, après les
virgules, après une conversion de type (cast) à la C et après le mot-clé
d'une instruction de contrôle. Ils ne doivent figurer ni entre le nom d'une
fonction et la parenthèse ouvrante d'un appel de fonction, ni immédiatement
à l'intérieur d'une paire de parenthèses :

    foo(i, j, l);
    if ((boolean) condition) {
        /* body */
    }

Conversions de type et sizeof
-----------------------------

Une conversion de type doit séparer l'opérateur de conversion de son
expression par une espace :
    '(char *) str'
'sizeof (type)' exige les parenthèses.  'sizeof expression' ne les exige
pas ; les utiliser n'est pas une erreur, mais les omettre évite d'encombrer
visuellement le code.  Les utiliser sans l'espace de séparation donne la
fausse impression d'un appel de fonction ou de l'expansion d'une macro avec
argument(s) ; 'sizeof' est un opérateur, et les parenthèses exigées autour
de '(type)' servent à le traiter comme une conversion de type.

Commentaires
------------

Certains commentaires de bloc sont sans décoration, simplement découpés en
lignes de largeur raisonnable :
    /* this is
       a comment */
Ils ne comportent généralement pas de ponctuation de phrase.

D'autres sont plus élaborés :
    /*
     * This is
     * another comment.
     */
Ce style s'emploie généralement avec une ponctuation de phrase, en
particulier s'ils contiennent plus d'une phrase.

Les commentaires de fin de ligne qui doivent s'étendre sur plusieurs lignes
    somecode(); /* this comment
                 * is ok */
doivent commencer chaque ligne de continuation par un astérisque, sinon
clang-format les convertirait en commentaire de bloc
    othercode(); /* this comment
                    should be avoided */
car ce commentaire serait converti en
    othercode();
    /* this comment
       should be avoided */
si un nouveau reformatage global était un jour effectué.  De même, plusieurs
commentaires destinés à être lus comme un seul
    morecode(); /* start of comment */
                /* more of comment  */
                /* end of comment   */
sont déconseillés, car les lignes suivantes perdraient leur indentation en
cas de reformatage.

De nombreux fichiers se terminent par
    /*filename*/
généralement précédé d'une ligne vide.  Il s'agissait d'un contournement
pour un commentaire - quelque part, peut-être dans le code Amiga ou Atari -
indiquant qu'un certain compilateur ne traitait pas toujours la dernière
ligne du fichier.  Si cette dernière ligne est un commentaire, rien n'est
perdu.  Le véritable problème venait presque certainement de fichiers source
qui ne se terminaient pas par un saut de ligne.  Aujourd'hui, nous essayons
d'imposer le saut de ligne final dans chaque fichier, au moins avant chaque
version, à défaut de le maintenir au jour le jour.  Le nom à la fin peut
toujours être utile lorsqu'on édite ou parcourt plusieurs fichiers.

Configuration de Vim
====================

Pour vim, les réglages suivants sont recommandés lors de l'édition du code de
NetHack, afin que l'indentation soit correcte :

    set shiftwidth=4
    set softtabstop=4
    set expandtab
    set tabstop=4
    set shiftround
    set textwidth=78
    set cindent
    set filetype=c


Configuration de Visual Studio
==============================

Dans Visual Studio, sous Tools->Options->Text Editor->C/C++, vous pouvez
définir les options suivantes pour obtenir le comportement souhaité :

[Tabs]
Indenting: Smart
Tab size: 4
Indent size: 4
Insert Spaces

Il existe sous [Formatting] un certain nombre d'autres options à vérifier
(Indentation, New Lines, Spacing et Wrapping), mais les entrées sont si
nombreuses qu'il serait peu pratique de les reproduire ici. Heureusement, les
options sont rédigées en anglais courant : il suffira de les parcourir avec
ce guide sous la main et d'effectuer les modifications nécessaires.

Configuration d'Emacs
=====================

Il existe sans doute une multitude de façons de gérer cela dans Emacs.
En voici une, à placer dans ~/.emacs.el :

(defun hook-c ()
  (setq c-set-style "k&r")
  (setq c-basic-offset 4)
  (setq indent-tabs-mode nil))
(add-hook 'c-mode-common-hook 'hook-c)
