Git est difficile à prendre en main. Ce fichier tente de servir d'aide-mémoire
pour les tâches de base, le temps que vous vous familiarisiez avec l'outil.

------------------------

[*] git checkout [-f] (branch)

Place votre dépôt local sur le commit le plus récent de (branch).
L'option -f abandonne les modifications faites dans le répertoire de travail.


[*] git status [-uall | -uno]

Affiche tous les fichiers modifiés de votre dépôt local, ainsi que la liste
de ceux que vous avez indexés (staged) pour le commit.
L'option -uall affiche en plus tous les fichiers non suivis de tous les
sous-répertoires.
L'option -uno n'affiche _aucun_ fichier non suivi.


[*] git log [-NUM]
[*] git log <commit1> <commit2>
[*] git log [--pretty=one]
[*] git log (branch)

Pour une explication complète de tous les arguments que l'on peut passer à
« log », consultez le manuel ; ils sont nombreux et ceux-ci ne sont que
quelques-uns des plus courants. Pour ce qui nous concerne, git log affiche
tous les commits selon les critères que vous indiquez :

-NUM : les NUM derniers commits de cette branche
<commit1> <commit2> : tous les commits entre commit1 et commit2
-pretty=one : affiche chaque entrée sur une seule ligne
(branch) : affiche les commits de (branch) au lieu de la branche courante

[*] git log --pretty=one --decorate --graph --all

(Le mieux pour comprendre est de l'exécuter et de regarder le résultat.)


[*] git add (filename)
[*] git nhadd (filename)

Ajoute les modifications apportées à (filename) à la zone de préparation du
commit (également appelée « index »).
 OU
Fait suivre un nouveau fichier par git.

« nhadd » est la syntaxe à privilégier : elle met automatiquement à jour les
en-têtes des fichiers source avec la date, la branche et la version les plus
récentes.  Voir Developer.txt pour les détails.


[*] git commit [-a] [-m "text"]
[*] git nhcommit [-a] [-m "text"]

Enregistre (commit) toutes les modifications indexées (dans l'index) sur
cette branche de votre dépôt local, à partir de votre position actuelle.
L'option -a effectue au préalable un « git add » de tous les fichiers
éligibles.
L'option -m utilise "text" comme message de commit au lieu d'ouvrir une
fenêtre d'éditeur pour que vous le rédigiez.

« nhcommit » est la syntaxe à privilégier : elle met automatiquement à jour
les en-têtes des fichiers source avec la date, la branche et la version les
plus récentes.  Voir Developer.txt pour les détails.


[*] git push [--all] [-u origin (branch)]

Envoie tous vos commits de la branche courante vers le dépôt central.
L'option --all envoie les commits de _toutes_ les branches.
L'option -u n'est nécessaire que la première fois que vous poussez une
branche (branch) que vous avez créée ; elle établit le lien entre la branche
locale et la branche distante.


[*] git reset [--hard] (filename)

Sans paramètre, retire de l'index les modifications de (filename) ; l'arbre
de travail n'est pas modifié. C'est l'équivalent de la commande
git reset --mixed (filename) ; git reset --soft (filename) n'a aucun effet.

Avec --hard, retire (filename) de l'index et ramène (filename) dans l'arbre
de travail à l'état du commit le plus récent.

*** ATTENTION *** --hard _va_ détruire vos modifications.

[*] git reset [--soft | --mixed | --hard] HEAD~1

*** ATTENTION *** Ne faites JAMAIS, au grand JAMAIS, cela sur un commit que
vous avez déjà poussé ; vous réécririez l'historique sur les machines
d'autres personnes, ce qui tourne généralement très mal.

Avec --soft, annule la dernière action « git commit », mais laisse les
modifications dans l'index et dans le répertoire de travail.

Avec --mixed, fait tout ce que fait --soft et retire en plus les
modifications de l'index. C'est le comportement par défaut si vous ne
précisez aucune des trois options.

Avec --hard, fait tout ce que fait --mixed et ramène en plus l'arbre de
travail au commit précédent.

*** ATTENTION *** --hard supprime de fait un commit et « perd » les
modifications.
[/fin de la zone sensible]


[*] git fetch [--all]

Récupère sur votre machine les commits du dépôt distant.
L'option --all récupère les commits de toutes les branches.
Ne les fusionne PAS dans votre dépôt local.


[*] git pull

Intègre dans votre dépôt les commits récupérés pour la branche courante et
met à jour votre position en conséquence. Cela crée un commit de fusion
(indiquant que vous avez fusionné une branche dans elle-même).


[*] git rebase [version sans argument UNIQUEMENT]

Intègre dans votre dépôt les commits récupérés pour la branche courante, puis
rejoue par-dessus vos commits et modifications locaux.

Illustration en art ASCII de grande qualité :

                                  E---F---G---H (modifications distantes)
                                 /
                                /
(branche 'frog')   A---B---C---D---E'---F' (vos modifications locales)

Après « git fetch » et « git rebase », cela ressemblera à ceci :

                                               --- (HEAD distant)
                                               |
                                               V
(branche 'frog')   A---B---C---D---E---F---G---H---E'---F'
                                                   ^    ^
                                                   |    |
                                                   -------- (à pousser)


[*] git branch (branch)

Crée une nouvelle branche à partir du commit sur lequel vous êtes placé.
Ne bascule pas automatiquement (checkout) sur cette branche.


[*] git checkout -b (branch)

Crée une nouvelle branche à partir du commit sur lequel vous êtes placé, et
bascule automatiquement sur cette branche.


[*] git branch <pattern> --list | [--all | -a] | [--remotes | -r]

Liste toutes les branches correspondant à <pattern>.
Avec --all à la place, liste toutes les branches (y compris celles suivies à
distance).
Avec --remotes à la place, liste uniquement les branches distantes.


[*] git merge (branch) [--no-commit]

Fusionne dans votre branche courante toutes les modifications de (branch)
depuis sa dernière divergence par rapport à un ancêtre commun.

Avec --no-commit, ne crée pas automatiquement d'entrée de fusion dans le
journal mais laisse tous les fichiers fusionnés dans votre répertoire de
travail ; pour terminer la fusion, vous devrez les enregistrer (commit)
manuellement plus tard (probablement après les avoir modifiés). Cela imite
plus fidèlement le comportement de fusion de svn [et de cvs ?]


[*] git stash [save | apply | list] <stashname>

save : prend toutes les modifications de votre répertoire de travail et les
met de côté (« stash ») dans une zone de stockage temporaire. Pratique si la
commande que vous voulez lancer refuse de fonctionner tant que le répertoire
de travail n'est pas propre ; pratique aussi pour déplacer des modifications
expérimentales d'une branche à l'autre sans avoir à les enregistrer.

apply : rejoue la remise (stash) nommée sur votre répertoire de travail
courant, comme s'il s'agissait d'un correctif (patch). Ne supprime pas la
remise de la liste.

list : liste tous vos blocs de code mis de côté.
