FEATURE_NOTICE : alertes pour une nouvelle version

Il existe un mécanisme dans le code pour avertir les joueurs d'un changement
de comportement par rapport aux versions précédentes du jeu.

Voici comment procéder :
   o À l'endroit où le changement de comportement doit alerter le joueur,
     - Ajoutez une instruction « if » qui déclenche l'alerte si la
       condition est remplie, par exemple
          if (flags.suppress_alert < FEATURE_NOTICE_VER(3.6.0))
             pline("Note: and explain the change here.");
     - L'exemple ci-dessus alertera les utilisateurs au sujet d'une
       fonctionnalité ajoutée en 3.6.0, par un message d'une ligne via
       pline(), mais vous pouvez faire plus élaboré (assurez-vous
       simplement que tout se fait dans le bloc de code du « if »).

Lorsque l'utilisateur estime que l'alerte n'est plus utile, ou qu'elle
devient agaçante, il peut définir l'option « suppress_alert ».
      - L'utilisateur ne peut régler suppress_alert que sur la version
        courante, et non sur des versions futures. Cette restriction
        permet d'utiliser cette fonctionnalité pour les nouveautés des
        versions suivantes.
      - La suppression peut se faire de façon interactive en cours de
        partie avec la commande 'O', ou via
           OPTIONS=suppress_alert:3.6.0
        dans le fichier de configuration de l'utilisateur.

PREFIXES_IN_USE et NOCWD_ASSUMPTIONS

Ces macros fournissent un mécanisme de stockage des chemins vers différents
types de fichiers. Ces chemins sont stockés dans le tableau fqn_prefix[]. Il
s'agit d'un mécanisme permettant de séparer les différents fichiers dont
NetHack a besoin.

Les préfixes sont ajoutés au début des noms de fichiers par diverses routines
de files.c, juste avant l'ouverture de l'un des types de fichiers utilisés
par le jeu.

Il ne s'agit pas d'options du fichier de configuration (même si ces options
seraient un moyen de donner des valeurs autres que celles par défaut à
certains chemins du tableau fqn_prefix[]). Évidemment, le tout premier chemin
nécessaire (aujourd'hui sysconfdir, auparavant configdir) ne peut pas être
défini par une option du fichier de configuration, mais le jeu doit tout de
même le dénicher « quelque part ».  Une fois ce « quelque part » déterminé,
cet emplacement (chemin) est stocké dans fqn_prefix[SYSCONPREFIX].  La façon
dont il y est stocké relève de nos choix de développeurs.

N'importe quelle entrée de fqn_prefix[] peut être définie d'une manière ou
d'une autre : dans le code de démarrage d'un portage, lors du traitement des
options, lors du traitement du fichier de configuration, en traduisant une
variable d'environnement du système comme USERPROFILE, ou de toute autre
façon souhaitée.  L'essentiel est que NOCWD_ASSUMPTIONS et PREFIXES_IN_USE
garantissent qu'il existe un endroit où stocker ces chemins.  Le code qui
*exploite* ces informations se trouve déjà dans files.c (voir fqname()).

Il existe une entrée de fqn_prefix[] pour stocker le chemin de chacun des
éléments suivants :
    PREFIX        NAME
0 HACKPREFIX     hackdir
1 LEVELPREFIX    leveldir    où créer les fichiers de niveau
2 SAVEPREFIX     savedir     où créer/lire les parties sauvegardées
3 BONESPREFIX    bonesir     où créer/lire les fichiers bones
4 DATAPREFIX     datadir     où lire data.base, etc.
5 SCOREPREFIX    scoredir    où lire/écrire le fichier des scores
6 LOCKPREFIX     lockdir     où créer/lire les fichiers de verrou
7 SYSCONFPREFIX  sysconfdir  où lire SYSCF_FILE
8 CONFIGPREFIX   configdir   où lire le fichier de configuration utilisateur
9 TROUBLEPREFIX  troubledir  où placer les fichiers panic, etc.

En résumé, ils servent à permettre « des chemins différents pour des choses
différentes », et à séparer :
- ce qui est en lecture seule de ce qui est en lecture-écriture ;
- ce qui relève de l'administrateur système de ce qui est modifiable par
  l'utilisateur ;
etc.

EXPRESSIONS RÉGULIÈRES

Plusieurs bibliothèques d'expressions régulières sont prises en charge.
Actuellement, un (et un seul) des fichiers suivants doit être lié lors de la
compilation :
  sys/share/cppregex.cpp
  sys/share/posixregex.c
  sys/share/pmatchregex.c

Cela permet d'accéder à différentes bibliothèques d'expressions régulières
du système, ou de se rabattre sur pmatch() si aucune n'est disponible.
cppregex.cpp utilise la bibliothèque d'expressions régulières de la norme
C++11 ; c'est le choix par défaut sous Windows.  posixregex.c utilise la
bibliothèque d'expressions régulières POSIX ; c'est le choix par défaut sur
les systèmes POSIX.  pmatchregex.c sert de solution de repli.

Les fichiers de configuration écrits pour l'un ou l'autre des deux vrais
moteurs d'expressions régulières sont compatibles entre eux, car il s'agit
dans les deux cas d'expressions régulières étendues POSIX. Les fichiers de
configuration écrits pour le moteur de repli ne sont pas compatibles.

D'autres implémentations d'expressions régulières peuvent être écrites. La
documentation complète de l'interface se trouve dans sys/share/posixregex.c

===========================================================
NOTES SUR LES FICHIERS D'EN-TÊTE

hack.h définit des valeurs disponibles pour tous les fichiers source de
NetHack, contient des enums et un certain nombre de définitions de struct
destinés à tous les fichiers source de NetHack.
hack.h ne contient ni déclarations ni définitions de variables.

decl.h et decl.c sont liés : decl.h contient les déclarations extern des
variables définies dans decl.c. Ces variables sont globales et disponibles
pour tous les fichiers source de NetHack.
Les définitions de variables de decl.c suivent en général à peu près le même
ordre que les déclarations correspondantes de decl.h.

Un nouveau fichier d'en-tête, cstd.h, a été ajouté lors du passage de la
version 5.0 au C99. Il inclut certains fichiers d'en-tête standard du C99.
